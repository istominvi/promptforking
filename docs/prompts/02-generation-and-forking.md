## Контекст

Мы строим **Promptforking** — сервис-галерею AI-генераций с механикой форкинга промптов. Каждая публикация — узел в дереве: её можно форкнуть, переписать промпт или параметры и опубликовать поверх.

Работаем в стиле `CLAUDE.md`: **думай до кода, минимум кода, хирургические правки, проверяемые цели**. Если что-то неясно — спрашивай до того, как писать.

### Что уже есть после спринта 1

- Каркас Next.js 16 (App Router) + TS strict + Tailwind v4, деплой на Vercel (`promptforking.vercel.app`), auto-deploy на push в `main`.
- Supabase auth через magic link. После логина создаётся `profiles` (триггер `handle_new_user`).
- Таблицы в `public`: `profiles`, `models` (4 сид-модели FLUX), `generations`. RLS включён везде.
- Главная `/` — заглушка ленты («Лента пока пуста»), `header.tsx` с email + «Выйти».
- Supabase-клиенты: `src/lib/supabase/{client,server,middleware}.ts` с `<Database>` generic. Типы — `src/lib/types.ts`.

**Ключевой факт:** таблица `generations` уже содержит всё для дерева форков — `parent_id`, `root_id`, `prompt`, `model_params` (jsonb), `model_id`, `image_url`, `status` (`pending`/`succeeded`/`failed`), `error`, `content_rating`, `is_public`. Триггер `generations_set_root_id` для корней (`parent_id IS NULL`) проставляет `root_id = id`. **Базовый форкинг не требует новой схемы.**

## Цель спринта

Оживить ядро продукта: залогиненный пользователь **генерирует картинку по промпту** через своего провайдера (BYO-ключ), **видит её в ленте**, **открывает**, **форкает** — правит промпт/параметры — и генерирует производную. Связи дерева — через `parent_id`/`root_id`.

## Решения MVP, на которые опираемся

Зафиксированы в `docs/SETUP_CHECKLIST.md` → «Принятые решения для MVP». Не пересматриваем:

- **Провайдеры:** Replicate + fal.ai. **Только BYO-ключ** — пользователь приносит свой ключ, мы не платим за инференс.
- **Форк-семантика:** дерево привязано к модели. Копируется промпт + параметры. **Смена модели = новый корень** (`root_id = self`, `parent_id = NULL`).
- **Публичность:** всё public по умолчанию (`is_public = true`).
- **Контент:** SFW only (`content_rating = 'sfw'`).
- **Медиа:** сохраняем URL картинки от провайдера, без своего хранилища.

## Открытые развилки (предложены дефолты — подтверди или поменяй до кода)

1. **Sync vs async генерация.** Дефолт: **синхронно** внутри server action, начинать с «быстрых» моделей (`*-schnell`, ~2–5 сек). Учесть лимит времени serverless-функции на Vercel. Async-поллинг/вебхуки — отложить, пока не упрёмся в timeout на медленных моделях (flux-pro).
2. **Где хранить BYO-ключ.** Дефолт: **только в браузере** (`localStorage`), ключ передаётся в server action на каждый запрос и **на сервере не сохраняется и не логируется**. Просто и безопасно — мы не несём ответственность за чужие ключи. Альтернатива (шифрование в БД через Supabase Vault/pgsodium) — сложнее, отложить.
3. **Визуализация дерева.** Дефолт: на `/g/[id]` — плоско: ссылка на родителя (если есть) + список прямых детей. Полный графический граф дерева — позже.

## Архитектура генерации

```
клиент (форма) ──┐
                 │ promptInput + apiKey (BYO, из localStorage)
                 ▼
        server action createGeneration
                 │ 1. insert generations { status: 'pending', author_id = auth.uid() }
                 │ 2. provider.generate({ model, prompt, params, apiKey })
                 │ 3a. ok  → update { image_url, status: 'succeeded' }
                 │ 3b. err → update { status: 'failed', error }
                 │ 4. revalidatePath('/') и '/g/[id]'
                 ▼
        провайдер-абстракция (lib/providers)
```

- **Провайдер-абстракция** `src/lib/providers/`: общий интерфейс `generate(input): Promise<{ imageUrl: string }>`. Выбор реализации по `models.provider` (`replicate` | `fal`).
- **BYO-ключ** приходит из клиента в server action как аргумент. **Никогда** не пишется в БД, не попадает в логи, не помечается `NEXT_PUBLIC_*`.
- **Server-only:** вся работа с ключами и провайдерами — в server actions / route handlers, не в client-компонентах.
- **SDK:** `pnpm add replicate @fal-ai/client` (проверь актуальные имена пакетов и API на момент работы). Опционально `zod` для валидации входных параметров.

## Acceptance criteria

- [ ] Залогиненный пользователь вводит свой Replicate (или fal) ключ; ключ **не уходит в БД** и не сохраняется на сервере.
- [ ] Форма: выбор модели из `public.models` (только `is_active`), поле промпта, базовые параметры из `default_params`; кнопка «Сгенерировать».
- [ ] Создаётся строка `generations`; при успехе показывается картинка; при ошибке — понятное сообщение и `status = 'failed'`, `error` заполнен.
- [ ] Лента на `/` показывает реальные генерации (`is_public = true AND status = 'succeeded'`), новые сверху. Заглушки больше нет.
- [ ] `/g/[id]` показывает картинку, промпт, модель, параметры, автора, дату.
- [ ] На `/g/[id]` кнопка «Форкнуть» → форма с **предзаполненными** промптом и параметрами → правка → новая генерация с `parent_id = исходная`, `root_id = root исходной`.
- [ ] Смена модели при форке создаёт **новый корень** (`parent_id = NULL`, `root_id = self`).
- [ ] `/g/[id]` показывает родителя (если есть) и прямых детей.
- [ ] RLS соблюдается: чужие непубличные/неуспешные генерации не видны; нельзя создать генерацию с чужим `author_id`.
- [ ] `pnpm lint`, `pnpm format:check`, `pnpm typecheck`, `pnpm build` — чисто.
- [ ] Поток работает на проде (`*.vercel.app`).

## Порядок работы

1. **Подтверди развилки** (sync/async, хранение ключа, отображение дерева) — предложи дефолты выше. Если сказано «на твоё усмотрение» — прими дефолты и явно их зафиксируй.
2. Провайдер-абстракция + SDK (`pnpm add replicate @fal-ai/client`).
3. BYO-ключ UI (`localStorage`) + чтение ключа в server action.
4. `createGeneration` (sync, начни с быстрых моделей).
5. Форма создания + интеграция со server action.
6. Реальная лента на `/`.
7. Детальная страница `/g/[id]`.
8. Форк: `forkGeneration` + префилл формы (учти смену модели → новый корень).

10. Прогон проверок → коммит (по-русски) → push → проверка на проде → пройтись по acceptance criteria.
